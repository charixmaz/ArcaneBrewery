# Historical document — integration removed

The integration described below was removed from the current Brewery release.
There is no economy API module, provider binding, selling command or payout path.
See [current standalone release notes](audit-reliability-fixes.md). Historical
transaction/escrow records and read-only `/brewmarket` diagnostics are retained.
Do not follow the old build or installation steps below for current versions.

# Shared economy API and optional Brewery integration

Starting point: master `2e3a95da8d5af23e61b036423e43f337ccf35355`.
Baseline verification passed: Brewery 267 tests, standalone Economy 21 tests.

## Artifact and classloader ownership

Three independently built Maven projects remain:

| Project | Artifact | Runtime content |
| --- | --- | --- |
| `arcane-economy-api/` | `arcane-economy-api-0.1.0-SNAPSHOT.jar` | Plain Java 25 API; no Paper/JDBC dependencies or plugin descriptor |
| `arcane-economy/` | `ArcaneEconomy-0.1.0-SNAPSHOT.jar` | Standalone provider, shared API, SQLite driver |
| Root | `ArcaneBrewery-1.0-SNAPSHOT.jar` | Brewery and its adapter; neither economy API nor economy implementation |

The existing four API types moved without changing their Java package names.
ArcaneEconomy shades the API without relocation. Brewery's API dependency is
`provided`; `softdepend: [ArcaneEconomy]` establishes optional startup/classloader
ordering for these Bukkit `plugin.yml` plugins. There is no hard dependency or
reflective service access. Do not install the API as another server plugin or
shade a private copy in consumers. See the
[API contract and third-party example](../arcane-economy-api/README.md) and
[Paper's plugin descriptor rules](https://docs.papermc.io/paper/dev/plugin-yml/).

`scripts/verify-economy-packaging.py` checks class names and bytecode: exactly the
API artifact's six class files must be present once in the provider, no economy
classes may leak into Brewery, and Brewery's descriptor must stay optional.
CI runs this check after independently verifying all projects and uploads the two
deployable plugins plus the developer API artifact. No Shade relocation was added.

## Optional lifecycle binding

`OptionalArcaneEconomy` has no public API type references. It loads a separate
connection only when the provider plugin is enabled, catching linkage errors so
missing/old API classes cannot disable Brewery. The connection obtains a typed
ServicesManager registration and publishes it atomically to worker callers.
Only enabled ArcaneEconomy-owned registrations are accepted. Missing service or
unsupported `apiVersion()` fails the operation closed.

Plugin enable/disable and service registration/unregistration update the binding.
Unregistration clears the captured registration directly, avoiding a lookup that
could republish an entry during its removal callback. No API classes are copied.
Disable stops accepting calls; the ledger also rejects fresh calls made through
retained provider objects. An already executing transaction may finish.

Normal startup, same-instance disable/re-enable and re-registration are supported.
Arbitrary live replacement of plugin classloaders is not a compatibility promise:
restart the server after updating JARs. If classes no longer match, operations fail
closed. Standard Paper 26.1.x / Java 25 is assumed, not Folia or reload utilities.

## Money, replay and uncertain outcomes

`EconomyPort` now accepts `BigDecimal`, as does the shared API. The adapter never
converts amounts/balances to floating point. Existing market valuation/pricing and
`MarketQuote.price()` remain unchanged. Settlement enters the exact-money boundary
once using `BigDecimal.valueOf` on that existing rounded quote; it never constructs
a decimal from the binary expansion of a double. Direct API/port callers can use
all supported exact decimal precision, including values beyond double precision.
The provider continues to enforce its configured scale and limits without rounding.

The adapter forwards the original transaction UUID. `APPLIED` succeeds; `DUPLICATE`
also succeeds only after transaction lookup verifies ID, operation, account, amount
and absence of a transfer target. Conflicting requests and all explicit rejection
statuses fail. Affordability is advisory and cannot reserve funds.

A write exception, malformed receipt or unverifiable replay raises
`EconomyOperationUncertainException`. This is intentionally different from a
confirmed rejection: the ledger might have committed before losing its response.
The existing settlement service leaves the journal reservation and removed asset
for reconciliation rather than restoring an item to an already-paid player.
Query/retry only the original request and transaction ID. No replacement ID is
generated by this integration.

## Threading and market call chain

Before this change, settlement existed only as a synchronous application service
and tests; no live market command/GUI or inventory adapter invoked it. Brewery now
offers the guarded `settleMarketSale(...)` integration entry point, requiring an
explicit journal and asset port. The call chain is:

1. Enqueue on a dedicated bounded single-worker executor (maximum 256 queued jobs).
2. Check quote expiry at worker execution time and run journal operations there.
3. Marshal asset removal/restoration to the Paper server executor.
4. Execute exact-money service calls on the worker. The adapter refuses calls on
   the server thread as an additional guard.
5. Commit/reject the journal on the worker and complete the future.

The worker may wait for an inventory handoff; the server thread must **never join
the returned future**. Future callbacks may execute on a worker: schedule player
messages/UI work back onto Paper. Disable closes pending handoffs/futures and
interrupts the worker without waiting on the server thread. This does not roll back
an in-flight external write: callers must reconcile any exceptional outcome.

## Verification and intentionally deferred risks

Commands (API install is the local artifact prerequisite):

```sh
mvn --batch-mode -f arcane-economy-api/pom.xml clean install
mvn --batch-mode clean verify
mvn --batch-mode -f arcane-economy/pom.xml clean verify
python3 scripts/verify-economy-packaging.py
```

Expected verified totals: Brewery **285**, Economy **22**, API **3** tests, no
failures/errors/skips. Existing ledger/migration suites remain intact. New tests
cover exact values, replay/conflict mapping, absent/incompatible API linkage,
provider replacement/removal/disable, retained closed ledgers, worker/server
separation, rejected scheduling, shutdown handoffs, uncertain writes and queue-time
quote expiry. Native Paper event dispatch/classloading remains a live check.

Local clean builds use fresh source/POM copies because the checkout's inherited
target deletion restriction persists. Source/POM SHA-256 comparisons verify the
copy matches the committed inputs. The API is not publicly published to Maven yet;
third parties need a source install or their own artifact repository.

No durable market journal or Bukkit asset escrow adapter was added: they remain
prerequisites for production player sales, exactly as documented in V1.19.
The caller-supplied journal must persist globally unique requests and reconcile
PREPARED/uncertain transactions. Inventory and SQLite are not one distributed
transaction; a crash cannot be solved by this API adapter alone. No commands/GUI,
Vault, pricing redesign, MySQL or drink identity changes are included.

Live checks still required:

- Start Brewery alone, Economy alone, and both; check normal plugin enable and
  brewing, service registration, commands and ledger persistence.
- Exercise a test integration through the async boundary; verify thread names,
  one payout for repeated IDs, conflicting-ID rejection and precision handling.
- Disable/re-enable the provider and unregister/re-register the service while
  Brewery stays enabled; operations must fail closed until a valid binding returns.
- Disable Brewery during queued/in-flight work; verify no queued inventory action
  runs afterward and reconcile uncertain IDs before any refund/retry.
- Restart after replacing plugin JARs and verify the provider and consumer share
  the API class identity on actual Paper. Do not test hot JAR swapping in production.
