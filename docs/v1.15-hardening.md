# V1.15 alchemy machine hardening

Reviewed against master `cca03cd`, Java 25 and the pinned Paper
`26.1.2.build.74-stable` API. The previous open-ended dependency range could
select a newer prerelease outside the target Minecraft version.

## Changes and invariants

- One inventory holder/session and task per world/core coordinate; all viewers
  share the same inventory. Closing a view never writes a stale inventory.
- Ordinary left/right transfers are calculated on copies and persisted before
  updating the GUI/cursor. Shift, number-key, double-click, offhand, drop,
  creative and top-inventory drag operations are blocked. Bottom-inventory
  ordinary clicks remain available.
- Processing captures an immutable source batch and additive plan. The base is
  exactly one completed fermented potion. Processing locks all machine inputs.
- Completion writes prepared output, remaining catalysts and COMPLETED status
  in one checked TileState update. Exactly one of each selected catalyst is
  consumed. Recovery validates the captured source/plan; completed output cannot
  be infused again. The first idle edit clears historical completion.
- Snapshot V2 is bounded and checksummed, with three native Paper item byte
  payloads. Expected previous bytes prevent stale writes. This checksum detects
  corruption, not deliberate edits by a privileged administrator.
- New saves use Paper `ItemStack.serializeAsBytes`/`deserializeBytes`, not Java
  object serialization. Legacy import has byte/depth/reference/class bounds,
  accepts only built-in item/meta aliases and rejects trailing objects. Invalid
  records remain untouched and unavailable rather than becoming empty slots.
- Startup and chunk reload reconcile timestamped operations. Unload, structure
  loss, shutdown and faults release tasks/views. Structure scans never force
  unloaded chunks. Rebuilding a structure resumes using wall-clock readiness;
  elapsed time continues while the structure is absent.
- Occupied or corrupt cores cannot be broken or removed by explosions. Normal
  enchanting remains untouched when the multiblock is absent.
- Alchemy preparation V1 remains readable; orphan/mixed payloads fail closed.
  Additives survive aging into canonical process/fingerprint identity. A failed
  canonical harvest retains its bottle instead of invoking legacy random stars.

## Verification

Baseline: 200 tests passed. Hardened: **226 tests, zero failures/errors/skips**,
`mvn --batch-mode clean verify`, including packaging/shading.
The checkout's inherited target-directory delete restriction required a fresh
temporary source/POM copy. All 193 source/resource/POM files were compared by
SHA-256 against that verified copy before commit (actual count is recorded in
the work log if the tree grows).

New tests cover snapshot framing/checksums/bounds/defensive copies, overflow,
GUI gesture policy, lossless slot transfers, input locking, catalyst doses and
consumption, metadata compatibility/rejection, aging additive identity,
seed-independent identity, atomic storage failures/stale writes, API TileState
compatibility and allowlisted legacy decoding without executing unknown Java
deserialization callbacks.

## Remaining runtime limits and review findings

This is an engineering acceptance of V1.15 subject to the live checks below;
no live server session was run. Unit tests inject native item serialization
and cannot certify actual Paper NBT migration or client event behavior.
EnchantingTable extends TileState in the pinned API.

Machine-local completion is atomic in the TileState update. It is not a durable
transaction across chunk storage and player cursor/playerdata saves. Abrupt
process termination between independent Minecraft saves can still duplicate or
lose transfers; no claim of filesystem-level exactly-once delivery is made.
Third-party plugins can also mutate inventories after event handling. Legacy
Wrapper migration relies on the target API's private map representation and
fails closed when unsupported. Quarantined data needs administrator inspection;
there is intentionally no destructive automatic reset.

Separate existing distillery concerns remain: independently opened GUIs,
processing input mutation, inventory/state completion saved separately, a dormant
DistilleryProcessTask and permissive UTF-8 decoding in DistilleryStateCodec.
Legacy cask inventory still uses Bukkit object serialization and its existing
GUI lifecycle. These were reviewed but not broadly redesigned in this alchemy
milestone. Canonical quality remains deterministic and bypasses random stars.
No V1.16 gameplay was started.

## Required live Paper checks

1. Ordinary enchanting without the multiblock; main/offhand interactions with it.
2. Two players opening the same core; closing/reopening while inputs change.
3. Shift, number keys, offhand swap, double-click, drag, drop and creative input
   before/during processing. Verify total item counts and locked inputs.
4. One/two/duplicate catalysts, completion with GUI closed, output removal and
   the next batch. Verify exactly one catalyst per selected slot is consumed.
5. Restart before/after readiness; chunk unload/reload and a chunk-border core;
   remove/rebuild support blocks, try piston movement, core break and explosions.
6. Copy a legacy machine save into a test world and verify real item/meta import;
   inject malformed snapshot/inventory PDC and confirm no reset or item removal.
7. Age prepared and unprepared copies using identical process settings; confirm
   additive-sensitive fingerprints and quality-seed-independent identity.
8. Force a canonical harvest validation error and confirm the source remains.
   Test abrupt server termination separately from graceful restart, with backups.
